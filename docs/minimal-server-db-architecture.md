# Minimal Server + DB-Centric Architecture

## 목표
게임 서버 소스 수정은 최소화하고, 상태/이벤트/피드백은 DB 또는 최소 API 훅으로 내보낸 뒤 AIA가 최대한 많은 운영 기능을 담당하도록 구성합니다.

## 권장 구조
- Game Server: 전투/이동/패킷/검증만 담당
- Game DB: 상태/이벤트/피드백/작업 큐 저장
- AIA: 판단/학습/자동화/관제/복구 담당
- Self-Hosted LLM: 보조 추론 담당

## 서버 최소화 원칙
- 서버에는 대형 AI 로직 넣지 않음
- observe payload 생성 최소화
- 결과 실행기(move/attack/skill/use item)만 유지
- 피드백 기록은 DB insert 또는 최소 REST 호출만 수행

## DB 중심 흐름
1. 서버가 캐릭터 상태를 DB에 기록
2. 서버가 중요 이벤트를 DB에 기록
3. AIA가 DB 또는 API를 통해 상태를 읽음
4. AIA가 결정/자동화/학습 수행
5. 서버는 결정 결과만 읽거나 받음
6. 서버는 최종 검증 후 실행
7. 실행 결과를 DB에 기록
8. AIA는 이를 학습 피드백으로 반영

## 단일 API 키 구조
- 서버와 AIA 사이에는 하나의 공용 API 키 사용 가능
- GitHub는 배포/저장소 접근용 키로 별도 관리 권장
- 운영 트래픽 키와 개발/배포 키를 혼용하지 않는 것이 안전

## 현실적 권장안
- 게임 서버 <-> AIA 통신용 API key 1개
- GitHub CI/CD 또는 저장소 접근용 token 1개 별도
- DB는 서버와 AIA가 공유 가능한 상태 저장/교환 계층으로 사용

## 왜 이렇게 해야 하는가
- 서버 소스 최소화
- 운영 기능은 AIA로 집중
- 대규모 로봇 운영 시 서버 부하 감소
- 장애 분석과 자동 복구를 AIA에서 집중 처리 가능
